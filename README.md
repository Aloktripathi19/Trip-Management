# Trip Management API

A backend service for creating trips and moving them through a validated status lifecycle.

**Stack:** Python 3.11 · FastAPI · SQLAlchemy 2.0 · PostgreSQL 16 · Alembic · pytest

## 1. Quick start (Docker)

Requires Docker with Compose.

```bash
docker compose up --build
```

This starts PostgreSQL, applies the Alembic migration, and serves the API on port 8000.

- Swagger UI: http://localhost:8000/docs
- OpenAPI JSON: http://localhost:8000/openapi.json
- Health check: http://localhost:8000/health

Stop with `Ctrl+C`; remove containers and data with `docker compose down -v`.

## 2. Local setup (without Docker)

Requires Python 3.11+ and a running PostgreSQL (13+).

```bash
# 1. Create a database and user
psql -U postgres -c "CREATE USER trips WITH PASSWORD 'trips';"
psql -U postgres -c "CREATE DATABASE trips OWNER trips;"

# 2. Create a virtualenv and install dependencies
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. Configure
cp .env.example .env               # edit DATABASE_URL if your DB differs

# 4. Apply the schema
alembic upgrade head

# 5. Run the API
uvicorn app.main:app --reload
```

### Configuration

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `postgresql+psycopg://trips:trips@localhost:5432/trips` | SQLAlchemy URL |
| `DB_POOL_SIZE` | `10` | Connection pool size |
| `DB_MAX_OVERFLOW` | `20` | Extra connections under load |
| `DEFAULT_PAGE_SIZE` | `20` | Default `page_size` |
| `MAX_PAGE_SIZE` | `100` | Upper bound for `page_size` |

### Database schema / migrations

The schema lives in `alembic/versions/0001_create_trips.py`.

```bash
alembic upgrade head       # apply
alembic downgrade base     # revert
```

`trips` table:

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key (generated by the app) |
| `trip_number` | `varchar(50)` | **Unique**, not null |
| `source` | `varchar(255)` | Not null |
| `destination` | `varchar(255)` | Not null |
| `driver_name` | `varchar(255)` | Nullable until assigned |
| `status` | `varchar(20)` | Not null, default `CREATED` |
| `created_at` | `timestamptz` | Default `now()` |
| `updated_at` | `timestamptz` | Default `now()`, refreshed on every update |

Constraints and indexes:

- `ck_trips_status`: status must be one of the five supported values.
- `ck_trips_source_ne_dest`: source and destination must differ.
- `ck_trips_number_not_blank`: trip number cannot be blank.
- `uq_trips_trip_number`: unique index, the authoritative duplicate guard.
- `ix_trips_status_created_at`: serves `GET /trips?status=...` sorted by newest.
- `ix_trips_created_at`: serves the unfiltered list.

## 3. Running the tests

The tests run against a **real PostgreSQL** because the concurrency behaviour depends on row locks and unique indexes. They build the schema with the real Alembic migration.

```bash
# create a separate test database once
psql -U postgres -c "CREATE DATABASE trips_test OWNER trips;"

source .venv/bin/activate
pytest
```

Override the target with `TEST_DATABASE_URL` if needed (default: `postgresql+psycopg://trips:trips@localhost:5432/trips_test`). **Warning:** the suite drops and recreates the `trips` table in that database.

Using Docker for the test database instead:

```bash
docker compose up -d db
docker compose exec db psql -U trips -c "CREATE DATABASE trips_test;"
pytest
```

What is covered (82 tests):
- Full transition matrix (every status pair), terminal-state rules.
- Input validation and duplicate trip numbers.
- Pagination, filtering, ordering, invalid query params.
- Delete rules and the consistent error envelope.
- **Concurrency** (8 simultaneous threads): duplicate creates, same-transition races, conflicting-transition races.

## 4. API reference and examples

Interactive docs: `/docs`. All examples assume `http://localhost:8000`.

### Status lifecycle

```
CREATED ──► ASSIGNED ──► IN_TRANSIT ──► COMPLETED
   │            │             │
   └────────────┴─────────────┴──────► CANCELLED
```

`COMPLETED` and `CANCELLED` are terminal. Nothing can move backwards or skip a step.

### Error format

Every error uses the same envelope:

```json
{
  "error": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "Cannot transition from ASSIGNED to CREATED",
    "details": { "current_status": "ASSIGNED", "requested_status": "CREATED" }
  }
}
```

| HTTP | `code` | When |
|---|---|---|
| 404 | `TRIP_NOT_FOUND` | Unknown trip id |
| 404 / 405 | `NOT_FOUND` / `METHOD_NOT_ALLOWED` | Unknown route or method |
| 409 | `DUPLICATE_TRIP_NUMBER` | `trip_number` already exists |
| 409 | `INVALID_STATUS_TRANSITION` | Transition not allowed from the current status |
| 409 | `TRIP_NOT_DELETABLE` | Deleting a trip that is not `CREATED`/`CANCELLED` |
| 422 | `VALIDATION_ERROR` | Bad body, query param or path param (`details` lists each field) |
| 422 | `DRIVER_REQUIRED` | Assigning a trip with no driver |
| 500 | `INTERNAL_ERROR` | Unexpected failure (details are logged, not leaked) |

### POST /trips: create a trip

```bash
curl -i -X POST http://localhost:8000/trips \
  -H 'Content-Type: application/json' \
  -d '{"trip_number":"TRIP-1001","source":"Delhi","destination":"Jaipur"}'
```

`201 Created` (with a `Location: /trips/{id}` header):

```json
{
  "id": "c45f42f5-c2ae-4265-bb18-086cd7ce8ff3",
  "trip_number": "TRIP-1001",
  "source": "Delhi",
  "destination": "Jaipur",
  "driver_name": null,
  "status": "CREATED",
  "created_at": "2026-10-01T16:30:14.019639+05:30",
  "updated_at": "2026-10-01T16:30:14.019639+05:30"
}
```

- Reusing an existing `trip_number` returns `409 DUPLICATE_TRIP_NUMBER`, including when two identical requests arrive at the same time (see [design decisions](#5-design-decisions)).

Body fields: `trip_number` (required, 1-50 chars, letters/digits/`. _ - /`), `source` and `destination` (required, 1-255 chars, must differ), `driver_name` (optional). Unknown fields are rejected.

### GET /trips: list with pagination and filtering

| Query param | Default | Rules |
|---|---|---|
| `status` | none | One of `CREATED, ASSIGNED, IN_TRANSIT, COMPLETED, CANCELLED` |
| `page` | `1` | `>= 1` |
| `page_size` | `20` | `1` to `100` |

```bash
curl 'http://localhost:8000/trips?status=ASSIGNED&page=1&page_size=10'
```

```json
{
  "items": [ { "id": "c45f42f5-...", "trip_number": "TRIP-1001", "status": "ASSIGNED", "...": "..." } ],
  "meta": { "page": 1, "page_size": 10, "total_items": 1, "total_pages": 1 }
}
```

Results are sorted newest first (`created_at DESC, id DESC`, so page boundaries are stable). A page past the end returns an empty `items` list.

### GET /trips/{id}: get one trip

```bash
curl http://localhost:8000/trips/c45f42f5-c2ae-4265-bb18-086cd7ce8ff3
```

`200` with the trip, `404 TRIP_NOT_FOUND`, or `422` if the id is not a UUID.

### PATCH /trips/{id}/status: update status

```bash
# Assign (driver_name required unless the trip already has one)
curl -X PATCH http://localhost:8000/trips/$ID/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"ASSIGNED","driver_name":"Ravi Kumar"}'

# Then move on
curl -X PATCH http://localhost:8000/trips/$ID/status \
  -H 'Content-Type: application/json' -d '{"status":"IN_TRANSIT"}'
```

`200` with the updated trip. `driver_name` is only accepted when `status` is `ASSIGNED`. An illegal move returns `409 INVALID_STATUS_TRANSITION`.

### DELETE /trips/{id}: delete a trip

```bash
curl -X DELETE http://localhost:8000/trips/$ID
```

`204 No Content` on success, `404` if missing, `409 TRIP_NOT_DELETABLE` if the trip is `ASSIGNED`, `IN_TRANSIT` or `COMPLETED`.

## 5. Design decisions

**Status transitions.** The allowed moves live in one table (`app/enums.py`) and are enforced in the service layer. Requesting the current status again is rejected as a non-transition, so a status can never silently "repeat".

**Concurrent status updates.** `update_status` runs `SELECT ... FOR UPDATE` on the trip row inside a transaction, then validates the transition against the status it just read, then writes and commits. Two simultaneous requests on the same trip are therefore serialised by the database: the second waits, re-reads the new status, and is rejected with `409` if its transition is no longer legal. Trips are locked individually, so different trips never block each other. Delete takes the same lock, so a delete cannot interleave with a status change. Verified by the tests in `tests/test_concurrency.py`.

**Duplicate `POST /trips`.** `trip_number` is the natural key and has a unique index, so the same trip can never exist twice. The application catches the `IntegrityError` and returns a clean `409 DUPLICATE_TRIP_NUMBER`. This is race-safe because the database makes the decision, not a read-then-insert check: of several identical requests arriving at once, exactly one gets `201` and the rest get `409` (verified in `tests/test_concurrency.py`).

**Validation.** Pydantic validates bodies (types, lengths, trimming, patterns, unknown fields rejected, source != destination) and query/path parameters. The database check constraints are a second line of defence.

**Layering.** `api/` (HTTP only) → `service.py` (business rules, transactions) → `repository.py` (queries) → `models.py`. Domain errors are exceptions mapped to the error envelope in one place (`main.py`).

**Pagination.** Offset-based with a total count. Simple, and fine for this scale (see improvements for keyset pagination).

## 6. Assumptions

- `CANCELLED` is allowed from `CREATED`, `ASSIGNED` and `IN_TRANSIT`. The brief lists only the forward path, so cancellation rules are my interpretation.
- A driver is required to reach `ASSIGNED`. `driver_name` is optional at creation and can be supplied at assignment.
- Deleting is a hard delete and only allowed for `CREATED` or `CANCELLED` trips, to avoid destroying in-flight or historical records. Change `DELETABLE_STATUSES` in `app/enums.py` to relax this.
- `trip_number` is case-sensitive and trimmed; `TRIP-1` and `trip-1` are different trips.
- Trip ids are UUIDs. Timestamps are stored and returned timezone-aware.
- No authentication or authorization, as it was out of scope.

## 7. Project structure

```
app/
  main.py          # app factory, error handlers, /health
  config.py        # settings from env
  database.py      # engine, session, get_db dependency
  models.py        # Trip ORM model, constraints, indexes
  schemas.py       # request/response validation models
  enums.py         # TripStatus + transition rules
  exceptions.py    # domain errors -> HTTP codes
  repository.py    # database queries
  service.py       # business logic + transactions + locking
  api/trips.py     # routes
alembic/           # migrations
tests/             # unit, API and concurrency tests
Dockerfile, docker-compose.yml, requirements.txt, .env.example
```
